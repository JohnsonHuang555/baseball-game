# V2 可玩 MVP：跟 V1 共存的入口、不依賴 DOM 的控制器、單一可寫分頁

Phase 3 把 V2 的放置經營接上畫面。專案是純 TypeScript + Vite，每個畫面是一個「清空 root、畫出畫面」的函式，所以 V2 也照這個方式做，不引入 UI 框架。

## V1 / V2 共存

- V1 首頁最上面加一張「放置經營（V2 新玩法）」卡片，下面標示「V1 原版棒球」，V1 原本的按鈕都不動。
- 進入 V2 時網址記為 `#v2`，重新整理後直接回到 V2；按返回會清掉 `#v2`，回到 V1 首頁。
- V2 只讀寫自己的 `dice-baseball.club.v3`，以及單一可寫分頁的標記 `dice-baseball.club.v3.writer`；不讀也不改 V1 的任何存檔，也不遷移 V1 的球員。

## 畫面結構（`src/v2/ui/`）

- `clubController.ts`：不依賴 DOM 的控制器，畫面只把 state 畫出來。所有寫入都走 Phase 2 的 application 入口（`createClubSafely`、`settleDue`、`claim`、`updateSettings`、`resetClubSafely`），不直接修改 `loadClub()` 讀到的資料再存回去。
  - **結算**：同一時間只跑一個，重複呼叫拿到同一個 Promise，所以畫面重繪不會多結算。觸發時機是進入 V2、回到分頁（`visibilitychange`、`focus`）、玩家按「更新進度」，以及倒數歸零時。倒數每秒用時間錨點重算，只是畫面。
  - **離開畫面**：`dispose()` 會用 AbortSignal 中斷進行中的結算，已經打完的場次照樣存檔；之後 async 操作完成也不會再更新畫面。
  - **回歸摘要**：只在進入或回到分頁、而且有新比賽時顯示；用 matchId 區間去重，同一份摘要只彈一次。
  - **領取**：先讀最新存檔。如果領取序號跟畫面上看到的不同，代表別的分頁已經領過，只更新畫面，不送出領取。
  - **錯誤**：
    - revision 衝突：重新讀取並提示，不會靜默覆蓋。
    - 寫入失敗、模擬失敗：顯示可以重試的錯誤。
    - 存檔損壞、版本不相容：顯示錯誤，不會自動清除。玩家可以下載備份，確認之後才用 `resetClubSafely` 刪除重來。
  - **其他分頁寫入**：收到 `storage` 事件就重新讀取。
- `writerGuard.ts`：瀏覽器沒有 Web Locks（`crossTab === false`）時，同一時間只有一個分頁可寫，以最後開啟或按「在此分頁繼續」的分頁為準。判斷依據是標記 key 目前的值，不靠事件先後。有 Web Locks 時每個分頁都可寫。
  - **寫入前確認**：控制器把存檔包上 `guardStore`。每一次存檔、建立、刪除，在寫進儲存的前一刻都會再確認一次身分；不是可寫分頁就丟 `read-only`，什麼都不寫。所以就算畫面還沒收到通知，或繞過畫面直接呼叫，唯讀分頁也寫不進去。
  - **接手時中斷**：A 正在離線結算時被 B 接手，A 一收到通知就中斷批次（AbortSignal，在下一場開打前停下）。原本中斷時會存下已打完的前幾場，但這一步也會被 `guardStore` 擋下，所以 A 不會寫入任何東西；那些場次由 B 依同樣的種子結算，結果相同，不會遺失。
  - **限制**：「確認身分」和「寫入」是兩個步驟。如果另一個分頁剛好在這兩步之間接手，仍然可能寫進去。這種情況靠 revision 檢查讓較晚存檔的一方失敗（conflict），提示重新讀取，不會靜默覆蓋，但這不是原子操作。沒有 Web Locks（或 IndexedDB 交易）就做不到完全保證，所以首頁在這種瀏覽器上會照實顯示這個限制，不宣稱跨分頁安全。
- `dashboardView`、`lineupView`、`tacticsView`、`reportView`：四個分頁的畫面，手機優先，底部導覽；樣式在 `v2.css`，沿用 V1 的 CSS 變數與按鈕。

## 陣容與戰術

**舊草稿不能覆蓋其他分頁的設定**：陣容與戰術各有一個版本，是內容指紋（`domain/fingerprint.ts` 的 `settingsVersions`）。

- 畫面建立草稿時記下當時的版本，儲存時交給 `updateSettings(deps, change, expected)`，在鎖內跟存檔目前的版本比對。
- 不一致（別的分頁已經改過並儲存）就丟 `settings-conflict`，不寫入。
- 陣容與戰術分開比對：別的分頁改了戰術，不影響這邊儲存陣容。
- 不用整份存檔的 revision 當版本，是因為每 5 分鐘的結算都會改 revision，那樣草稿幾乎一定會過期。
- 衝突或收到別的分頁寫入時，控制器讀進最新存檔，但畫面上的草稿不會消失：存檔列改成「草稿是根據舊設定做的，無法直接儲存」，儲存鈕停用，玩家按「載入最新設定（捨棄草稿）」才會捨棄。
- 有未儲存的草稿時離開 V2，會先確認。

**建立球團的表單**：失敗原因（寫入失敗、已有存檔、非預期錯誤、名稱不合法）記在控制器的 `createError`，輸入的名稱留在畫面的 `draftName`，所以表單因為狀態改變重繪時，錯誤訊息和名稱都還在，可以直接重試。

- **陣容**（`domain/lineup.ts`）：調整重用 V1 的 `swapSlots`、`swapPositions`，有換人、交換守位、交換棒次、換先發投手四種。儲存前用 `lineupIssues` 檢查：9 人、9 個守位各一、身分正確、不重複、隊長在先發。`validateClub` 和 `applySettingsChange` 也會檢查，所以不合法的陣容進不了存檔。
- **自動排陣**：重用 V1 的 `bestArrangement`（最多羈絆排法）。它只比羈絆與守位適性，不看能力值，所以按鈕沿用 V1 的名稱，套用前先列出會改哪些人讓玩家確認，不包裝成「能力最佳陣容」。
- **戰術**（`domain/tactics.ts`）：只開放均衡戰術的三個選項，所有換算集中在這裡：
  - 跑壘積極度：積極、均衡、保守，盜壘門檻分別是 0.65、0.75、0.85。
  - 後段調度：開或關。
  - 犧牲觸擊：開或關。

  `coachParamIssues` 檢查參數範圍，讀檔和儲存時都會驗證。

## 戰報

每場都保留摘要，可以顯示勝敗、比分、局數、精彩事件和獎勵。最近 3 場有完整的 MatchReplay，會用 V1 的 `replay()` 重播，算出每局比分與我方個人成績。沒有 replay 的舊比賽只顯示摘要，也就是遵守 Phase 2 的保留上限。
