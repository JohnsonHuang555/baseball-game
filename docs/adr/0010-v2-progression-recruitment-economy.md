# V2 養成、招募、經濟支出與存檔遷移（schemaVersion 3 → 4）

Phase 4 讓 V2 有可以持續玩下去的循環：自動比賽 → 獲得資金與經驗 → 升級或招募球員 → 調整陣容 → 影響後續比賽。

## 1. 為什麼要改資料模型

V3 的 `roster` 直接內嵌球員物件（模擬用的 Roster）。這種結構有三個問題：沒有地方放「不在陣容裡的球員」，球員沒有等級，而且只要換下陣容，那名球員就會從存檔消失。所以 V4 把資料分成三層：

| 層 | 存在哪裡 | 內容 |
|---|---|---|
| 永久球員資料 | `players: PlayerRecord[]` | 原始能力（Lv.1）、等級、加入方式、加入時是第幾場。ID 永遠不變 |
| 陣容配置 | `roster: RosterAssignment` | 只存 ID：9 位先發與守位、板凳 2 人、先發投手、後援 2 人、隊長。其他人是預備名單 |
| 單場快照 | 每場比賽的計畫（`planMatch`） | 開打前用 `resolveRoster()` 把 ID 換成**養成後的能力**，再深拷貝一份交給 V1 引擎 |

- **能力的唯一來源**：養成後的能力由「原始能力 + 等級」確定性算出來（`domain/progression.ts`），不另外存一份。所以存檔、畫面、比賽用的能力不可能對不起來。
- **陣容人數**：上場名單維持 14 人（9 + 2 + 1 + 2），跟 V1 引擎、自動教練完全相容。新球員一律先放進預備名單。
- **引擎不知道養成**：V1 的 `Game` 只收到換算好的 Roster，養成資料沒有綁進引擎。
- **舊比賽不受影響**：已存的 MatchReplay 裡是當時的快照，之後升級不會改變它。

## 2. 能力成長（`domain/progression.ts`、`domain/progressionConfig.ts`）

- **範圍**：能力是 1～10（產生時是整數，V1 的成長與裝備用 0.5 為單位，上限 10）。等級是 Lv.1～Lv.20，不能降級、不能重置。
- **Lv.20 的總成長**：
  - 打者：流派那一項 +2.0，其他三項依原始能力高低 +1.2、+0.9、+0.6（力量型偏力量、技巧型偏打擊、速度型偏速度、防守型偏守備）。
  - 投手：球威、控球較高的那一項 +2.0，另一項 +1.4，耐力 +0.8。
- **遞減**：第 L 級拿到總成長的 ((L−1)/19)^0.6，前面成長快、後面每級越來越少。
- **上限**：任何能力都不超過 10。
- **公平性**：不分稀有度，成長幅度都一樣，高能力的球員反而先碰到上限，所以不會讓高稀有度壟斷所有策略。
- **確定性**：相同的球員和等級，結果一定相同（純函式、不抽亂數）。

## 3. 成本曲線（由 `scripts/balance-v2.ts` 反推）

**實測收益**：初始球隊對同強度的對手，每場約 90 資金、10 經驗。一天上線 2 次（每次都碰到離線 8 小時上限）約 192 場，等於 17,500 資金、1,900 經驗。

| | 公式／數值 |
|---|---|
| 升級 Lv.L → L+1 | 經驗 = round(40 × L^1.3)（取 5 的倍數），資金 = 經驗 × 8 |
| Lv.1 → 2 | 320 資金、40 經驗（約 4 場） |
| 單人累計到 Lv.5 | 4,400 資金、550 經驗（半天以內） |
| 單人累計到 Lv.10 | 24,600 資金、3,075 經驗 |
| 單人累計到 Lv.20 | 128,880 資金、16,110 經驗（每天 2 次約 8～9 天） |
| 招募第 n 次（從 0 起算） | 4,000 + 800 × n 資金，不花經驗；最多 30 人（初始 14 人，最多再招 16 人，共 288,000 資金） |

調整過程：

1. 第一版資金倍率是 4。模擬後發現經驗才是瓶頸，只升級的玩家 14 天累積了 15 萬沒用到的資金，招募幾乎是免費的附加收益。
2. 把資金倍率提高到 8，讓資金在升級和招募之間有取捨。
3. 招募成本從 2,500 + 500n 提高到 4,000 + 800n，避免一週內就招滿。

## 4. 經濟與冪等支出（`application/economyService.ts`）

**帳務不變量**：`assets + unclaimed + spent = earned`，資金、經驗分開驗證，讀檔時也會檢查。

- `earned`：所有收入（比賽獎勵；之後的免費獎勵、退款也算收入）。
- `spent`：所有支出，只增不減。之後如果要做退款，記成收入，不倒扣 `spent`，累計數字才不會被改寫。

**升級和招募共用同一套支出流程**：

- **序號**：請求帶上讀到的 `nextOpSeq` 和請求內容（requestKey，例如 `upgrade:<id>:<目前等級>`）。
  - 序號等於目前值：執行。
  - 序號是上一個、而且內容相同：這是重送，回傳原本那一筆，不再扣款。
  - 其他情況：拒絕（`stale-request`），請重新讀取。
- **等級檢查**：升級另外帶「預期等級」，跟存檔不同就拒絕，所以一個請求不會讓球員連升兩級。
- **在鎖內完成**：讀最新存檔 → **先用舊能力結算到期的比賽** → 檢查資產 → 扣款並改球員資料 → 一次存檔。
  - 資源和球員資料在同一份存檔裡一起寫入；寫入失敗就什麼都沒變。
  - 因為先結算，所以不能在離線 8 小時後先升級、再用新能力回頭打完那 8 小時的比賽。
- **多分頁**：有 Web Locks 時排隊執行；沒有時，存檔前的 revision 檢查讓較晚的一方失敗。兩種情況資產都不會變成負數。
- **招募的亂數**：由「球團種子 + 招募次數 + 打者／投手」決定，所以失敗後重試會抽到同一位球員，不會重抽又重複扣款。
- **球員 ID**：用既有產生器的亂數 ID，跟現有球員撞到就繼續產生下一位。不用名單長度當 ID，所以之後刪除球員也不會撞號。
- **紀錄**：支出紀錄只保留最近 30 筆，每筆有原因、球員、金額、時間、請求內容；累計總額永久保存在 `spent`。

## 5. 存檔遷移（`domain/migration.ts`、`ClubRepository.migrateClub`、`application/clubLifecycle.openClubSafely`）

1. **偵測**：只看 `schemaVersion`。是 3 時 `loadClub()` 丟 `needs-migration`，不會被當成損壞，也不會被要求刪除重來。
2. **執行**：進入 V2 時，`openClubSafely` 在 ClubLock 裡呼叫 `migrateClub()`：
   - 讀原始文字。
   - 在記憶體裡遷移：純函式、確定性，不讀時間、不抽亂數。
   - 把原始文字**逐字**寫進備份 key `dice-baseball.club.v3.backup-schema3`。
   - 寫入前再讀一次原始文字，確認沒被改過。
   - 寫入升級後的存檔。
   - 遷移結果：既有球員一律 Lv.1，ID、能力、特性、流派、陣容、資金、經驗、戰績、結算游標、時間錨點、戰報都不變；不重新產生球員，不重新結算比賽。`earned` = 原本的 `lifetime`，`spent` = 0，revision 加 1。
3. **失敗**：
   - V3 本身不合法、或遷移結果沒通過 V4 驗證：`migration-failed`，原本的存檔一個字都不動，畫面提供原始存檔下載。
   - 備份或主存檔寫入失敗：`write-failed`，主存檔還是 V3，下次進入會重新遷移（不會有寫到一半的存檔，因為主存檔只寫一次）。
4. **多分頁重複遷移**：
   - 有 Web Locks：其他分頁排隊，輪到時讀到的已經是新格式。
   - 沒有 Web Locks：寫入前比對原始文字，被搶先的一方收到 `conflict`，重新讀取就是新格式。
   - 遷移是確定性的，所以不管哪個分頁寫入，結果都一模一樣。
   - 唯讀分頁（單一可寫分頁限制）不會自己遷移，會提示到可寫分頁完成。
5. **不換 storage key**：原地升級、沿用 `dice-baseball.club.v3`（名稱是第一版留下來的）。
   - 換新 key 的問題：還開著 Phase 3 程式的分頁會繼續寫舊 key，那些進度會默默遺失。
   - 沿用同一個 key：舊分頁讀到 schemaVersion 4，會判定為版本不相容而停止寫入（Phase 3 的 `saveClub` 寫入前會重新讀取驗證）。
   - 備份 key 遷移後不再寫入，也不會自動還原；「刪除存檔重新開始」只刪主存檔。
   - V1 的存檔（錦標賽、進度、偏好）完全不碰。

## 6. 平衡模擬結果（14 天、3 個球團種子平均）

**假設**：每天上線 2 次（間隔 12 小時，每次都碰到 8 小時上限，一天 192 場），每次「結算 → 領取全部 → 依策略花錢」。對手固定是平均能力 5 的隊伍。

| 策略 | 第 14 天上場平均能力 | 第 8～14 天勝率 | 上場平均等級 | 球員數 |
|---|---|---|---|---|
| A 完全不養成 | 5.09 | 50% | 1.0 | 14 |
| B 平均養成 | 5.77 | 64% | 8.3 | 14 |
| C 集中養成（5 位主力） | 5.40 | 59% | 5.1 | 14 |
| D 招募優先，再平均養成 | 5.96 | 75% | 7.4 | 27 |

一天只上線 1 次時（一天 96 場）：B 59～60%、C 55%、D 70%，進度大約是一半。

- **平均養成 vs 集中養成**：平均養成比較有效，因為成長遞減，加上 14 人都會上場。
- **D 最強，但有代價**：它同時用到兩種資源，而且可以在每個守位挑最好的新人。代價是第 14 天還有 7,800 經驗沒用（資金都花在招募），而且第 14 天才招到 27 人。
- **只花一種資源的策略都比較差**：只升級（B）會剩下 4.6 萬資金沒用。
- **沒有完全壓倒其他策略的單一選擇**：「招募 + 升級」最好，這是兩個系統都有用的正常結果。
- **人數上限**：照這個速度，大約 2～3 週會碰到 30 人。到時候招募的錢會回到升級。之後如果要持續招募，需要「放生／交易」釋出名額（Phase 5，見限制）。

## 7. 限制

- **勝率會一直上升**：對手強度固定、沒有聯盟升降級，所以養成之後勝率會持續上升（第 14 天 60～75%）。之後的聯盟系統要讓對手跟著球團變強。
- **最多羈絆排法**：只在先發和板凳之間排，不看預備名單（從最多 30 人挑 9 人的組合數太大）；而且照舊不看能力值。
- **30 人上限**：沒有放生或交易；滿了只能繼續升級。
- **獎勵與成本**：都是暫定的，集中在 `domain/config.ts` 與 `domain/progressionConfig.ts`。
