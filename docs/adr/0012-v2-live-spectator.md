# V2 即時觀戰（Live Spectator）、固定比賽計畫、歷史 Box Score 與 schemaVersion 7

Phase 5B 原本（PR #9 第一版）做的是「觀看已經打完的比賽重播」。產品方向調整後改成：**以正在進行中的比賽觀戰為核心，歷史比賽只保留數據戰報**。原因是玩家更想看自己的球隊「現在」怎麼比賽，而不是重看已經知道結果的場次。V2 仍然是放置型經營：可以看，但不用手動打擊、投球或逐球下決策。

## 1. 現有放置引擎的時間語意

| 項目 | 值或行為 |
|---|---|
| `MATCH_INTERVAL_MS` | 5 分鐘一場，一場接一場，沒有空檔 |
| `MAX_OFFLINE_MS`／`MAX_BATCH_MATCHES` | 離線最多算 8 小時，也就是 96 場 |
| `idle.anchorMs` | 結算後就是第 `idle.nextMatchIndex` 場的開始時間 |
| `dueMatches()` | 算出 `floor((now − anchor) / 5 分鐘)` 場到期，封頂 96 |
| `advanceAnchor()` | `anchor = max(anchor, now − 8h) + n × 5 分鐘`，超過 8 小時的時間捨棄 |
| `planMatch()` | 比賽計畫（陣容、能力、戰術、聯盟、種子），**原本在結算時才用「最新的球團」建立** |
| `settleDueUnsaved()`／`settleOutcomes()` | 打完到期的比賽、記帳、推進游標與錨點 |

所以「第 N 場」的實際時間是 `[anchor, anchor + 5 分鐘)`，結束後才能結算。

**問題**：計畫是在結算時才建立的，所以比賽進行中升級、換陣容，會改變這一場的結果。直播時畫面上看到的比賽，可能跟最後結算的不一樣。

## 2. 兩個方案

| | A. 觀看時逐球推進 `Game` | B. 結果先確定，畫面依時間同步（採用） |
|---|---|---|
| 結果 | 跟無畫面的結算是兩條路，容易不一致 | 跟無畫面的結算是同一個計算（同一份計畫、`runMatch`） |
| 關閉頁面、切換分頁 | 中途狀態要另外存，關掉就斷 | 不用存任何畫面狀態，進度只由時間決定 |
| 多分頁 | 兩個分頁可能各自推進出不同結果 | 每個分頁算出來的都一樣 |
| 離線、時間到期 | 要跟離線補算協調 | 照原本的結算流程 |
| 代價 | — | 要定義計畫何時固定、動畫怎麼對應真實時間 |

## 3. 固定比賽計畫（`application/liveMatch.ts`）

**規則**：任何會改變比賽計畫輸入的操作，都在 ClubLock 裡依序做三件事：
1. 結算到期的比賽。
2. 用**修改前**的狀態固定進行中那一場（`liveMatch = { matchIndex, plan }`）。
3. 套用修改。

會改變計畫輸入的操作是：換陣容／戰術（`updateSettings`）、升級／招募／釋出（`spendSafely`）、晉級挑戰（`challengeNextLeague`）。

**為什麼正確**：球團只會被寫入操作改變。所以進行中那一場開賽之後的第一次修改，「修改前」的狀態就等於開賽當下的狀態。如果開賽後一直沒有任何修改，用目前的球團算出來的計畫就是開賽時的計畫，所以不需要寫入（觀戰是唯讀的）。

**因此**：
- 同一場比賽不因重新整理、關閉觀戰、切換分頁或裝置而改變。對手由種子決定，陣容、能力、戰術、聯盟在開賽時就確定。
- 觀戰期間升級、換陣容、晉級，都不影響已經開始的比賽；新設定從下一場生效（`effectiveFromMatch` 是下一場，畫面提示「從第 N+1 場開始生效」）。
- **結算**：那一場一定用固定的計畫，收到別的計畫就丟 `mismatch`。結算完就清掉 `liveMatch`。
- **晉級時的例外**：進行中那一場固定在舊聯盟，結算時接受它的聯盟跟球團目前的不同。收益照舊聯盟的倍率計算，但不算進新聯盟的戰績。
- **不觀看也一樣**：結算流程沒有變，只是改用固定的計畫。同一場只結算一次（結算游標）。不能在預定結束時間之前結算，也不會因為觀看而多發或少發獎勵。
- **時間倒退**（現在比錨點早）：進行中那一場的開始時間在未來，畫面顯示「即將開始」倒數；如果這時修改球團，計畫照樣先固定。

## 4. 直播同步（`currentLiveMatch`、`LiveSchedule`、`LivePlayer`）

- **哪一場在進行**：用跟結算相同的函式推算，進行中的是 `nextMatchIndex + 到期場數`，開始時間是 `advanceAnchor(anchor, now, 到期場數)`。唯讀分頁沒辦法結算時，也推算得出同一場。
- **時間軸**：用固定的計畫跑一次 `runMatch`（跟結算同一套計算），再用 PR #9 的 `buildTimeline` 轉成逐格事件與狀態，每場約 3.6 ms、約 254 格。
- **對應到 5 分鐘**：每一格依事件種類給權重（跟 V1 的動畫節奏同比例），把 `[0, 5 分鐘)` 依權重分配給各格。開賽後經過 t 毫秒，就是 `positionAt(t)` 那一格。
- **`LivePlayer`**：
  - 進來時直接跳到目前那一格，不會從第一球播一場已經打了兩分鐘的比賽。
  - 每一格的動畫縮放到這一格剩下的時間裡；播完了就等到下一格的時間。
  - 畫面落後（背景分頁、暫停後繼續）時，直接同步到當下的進度，不補播中間錯過的球。
- **暫停只停自己的畫面**：比賽時間照走，剩餘時間照樣倒數。畫面上寫明「比賽仍在進行」，繼續時同步到目前進度。
- **直播沒有的操作**：重播、跳到結束、調速度。這些在直播中會讓人誤會比賽被暫停或可以改變。
- **比賽結束**：到了預定結束時間才顯示最終比分。獎勵在一般結算時才加到未領取，畫面上也這樣說明。「觀看下一場」會先結算，再進入下一場。
- **重新整理、切換裝置**：重新推算，回到正確的進度。切到背景時畫面停住，回到前景時同步。
- **離線 8 小時後回來**：照原本的規則補算（最多 96 場，固定的那一場用固定的計畫），再顯示目前進行中的那一場。

## 5. 歷史戰報：Box Score

- **結算時存精簡數據**（`domain/boxScore.ts`）：每局比分、雙方安打與失誤、我方打者 `[名字, 打席, 安打, 全壘打, 打點, 三振]`、我方投手 `[名字, 出局數, 失分, 三振]`，另外存預定結束時間 `playedAt`。看戰報時不用重新模擬整場。
- **戰報內容**：日期、聯盟、對手、比分、勝敗、每局比分（R／H／E）、打者與投手成績、精彩事件、收益。
- **保留範圍**：只保留最近 50 場（`RETENTION_CONFIG.recentMatches`），畫面上寫明，不宣稱永久可查。
- **大小**：每場約 0.38 KB，50 場約 19 KB。96 場離線結算後存檔約 71 KB，30 人球團約 82 KB，最高聯盟、長期遊玩約 90 KB。
- **舊比賽**：
  - 還保留完整 Replay 的近期比賽（最多 3 場），遷移時用 Replay 確定性重算 Box Score（比分不一致就不補）。
  - 其他舊比賽只有摘要，畫面寫明「存檔升級前結算的比賽，只保留比分、精彩事件與收益」。
- **移除的部分**：戰報的「觀看比賽」、首頁的「觀看最近比賽」，以及開戰報時重新跑 `replay()` 的流程。
- **保留的部分**：`replays` 欄位（最近 3 場的 MatchReplay），作為確定性的稽核資料與遷移時重算 Box Score 的來源，不再出現在畫面上。

## 6. 晉級挑戰的觀看（P2）

挑戰流程沿用 Phase 5A 已經驗證過的模型：按下時在鎖內驗證、模擬、更新聯盟、發獎，一次存檔。不同的是，畫面**先不揭曉結果**：
- 先問要「觀看挑戰過程」還是「直接看結果」。關掉這個提問等於直接看結果。
- 觀看時用存好的 `challengeReplay` 播放，可以暫停、1×／2×／4×、直接看結果。播完、直接看結果、中途離開，都會顯示結果。
- 中途重新整理或離開：結果已經存檔，不會消失。首頁聯盟卡片有「觀看上次晉級挑戰」。
- 同一個 requestId 重送、多分頁同時挑戰：沿用 5A 的序號與 requestId，不會重複挑戰或發獎。
- 寫入失敗：沒有存檔，也不會進入觀看或顯示結果。

**沒有做的**：依時間排程的挑戰直播（例如「挑戰賽 5 分鐘後打完」）。這需要新增「挑戰進行中」的持久化狀態，並把挑戰拆成建立、進行、完成三步，會動到 5A 穩定的挑戰與獎勵模型，所以拆到後續 PR。

## 7. 存檔：schemaVersion 7

- `liveMatch: { matchIndex, plan } | null`。驗證規則：只能是 `nextMatchIndex` 那一場，`matchId` 一定屬於這個球團。只在比賽進行中修改球團時才有，約 6 KB，結算後清掉。
- 每場比賽多了 `box?` 和 `playedAt?`（選填，舊比賽沒有）。
- **遷移**：
  - V6（PR #9 第一版的草稿格式）→ V7。V3、V4、V5 依序升上來。
  - 原始文字備份到 `…backup-schema6`，沿用 Phase 4 以來的安全順序與「不覆寫有價值的備份」規則。
  - `nextMatchIndex`、`anchorMs`、聯盟、經濟、挑戰 Replay 都不動，不重算比賽、不重複發獎。
- **Fixture**：`club-v6-phase5b.json` 是用 PR #9 第一版的程式實際跑出來的存檔（150 場、晉級過一次、有挑戰 Replay）。
- 還開著舊版程式的分頁讀到 7 會判定版本不相容，停止寫入。

## 9. 驗證（虛擬時鐘）

- **情境 A～E**（同一個種子、同一份球團，第 2 場在 10:00～15:00）：A 全程不看、B 從開賽就看、C 打到 12:30 才進來、D 看到一半離開再從新分頁回來、E 看的時候升級第一棒並換陣容。五個情境的第 2 場比分、勝敗、精彩事件、Box Score、獎勵完全相同。E 的第 3 場才用新的等級與陣容。
- **時間邊界**：14:59 沒有東西可以結算，15:00 才結算。開賽瞬間在第 0 格，結束前一刻在最後一格；時間倒退時顯示即將開始。
- **一致性**：多分頁同時固定計畫與結算，只結算一次，用同一份計畫。離線 10 小時後補算 96 場。
- **畫面測試**：中途加入、暫停只停畫面、繼續時同步、看到結束、觀看下一場、觀戰不寫入、觀戰中升級不影響這一場、快速開關。

## 10. 限制與後續

- 依時間排程的晉級挑戰直播：見第 6 節，拆到後續 PR。
- 直播沒有逐局跳轉、精彩片段；換人只有文字提示。
- 歷史戰報只保留最近 50 場，更早的需要另外設計儲存方案。
- `replays`（3 場、約 20 KB）不再出現在畫面上，之後可以評估縮減。
