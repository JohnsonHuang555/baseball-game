# 骰子棒球 V2：放置經營（開發說明）

V2 是放置型的棒球經營：玩家管理球團、陣容與戰術，比賽由自動教練打完，每 5 分鐘一場，離線也會繼續（最多算 8 小時）。V1（逐球操作的原版）完全保留；首頁最上面是 V2 入口，網址 `#v2` 會直接進 V2。

## 功能

| 功能 | 說明 |
|---|---|
| 建立球團 | 第一次進入時建立，初始 14 人（9 先發、2 板凳、1 先發投手、2 後援）由既有產生器產生 |
| 自動比賽 | 每 5 分鐘一場，用 V1 的模擬引擎與自動教練；離線最多算 8 小時（96 場） |
| 收益 | 每場給資金與經驗，結算後要「領取」才會變成可以花的資產 |
| 球員養成 | Lv.1～20，花資金與經驗升級，能力依流派成長、逐級遞減、上限 10；升級後從下一場尚未打的比賽開始生效 |
| 招募 | 花資金招募打者或投手（Lv.1），先放進預備名單；球團最多 30 人 |
| 陣容 | 換人上場（含預備名單）、交換守位或棒次、換先發投手、最多羈絆排法；從下一場開始生效 |
| 戰術 | 初版均衡戰術：跑壘積極度、後段調度、犧牲觸擊 |
| 戰報 | 近期 50 場摘要，最近 3 場可以看每局比分與個人成績 |

## 程式結構（`src/v2/`）

| 目錄 | 內容 |
|---|---|
| `domain/` | 純資料與純函式：存檔格式（`club.ts`）、養成（`progression.ts`、`progressionConfig.ts`）、招募（`recruitment.ts`）、陣容（`lineup.ts`、`roster.ts`）、戰術、遷移（`migration.ts`、`legacyV3.ts`）、獎勵與常數（`config.ts`、`rewards.ts`） |
| `application/` | 自動教練、比賽執行、放置時間、批次、結算、領取、升級與招募（`economyService.ts`）、建立／重設／遷移入口（`clubLifecycle.ts`） |
| `infrastructure/` | localStorage 存檔、Web Locks、依賴組裝（`createV2Deps`）、系統時間 |
| `ui/` | 控制器（不依賴 DOM）與各個畫面 |

設計決策見 ADR-0007（自動比賽）、0008（放置結算）、0009（可玩 MVP）、0010（養成、招募、經濟、遷移）。

## 存檔

- localStorage key `dice-baseball.club.v3`，目前是 schemaVersion 4。舊的 schemaVersion 3 會在進入 V2 時自動升級，原始文字備份在 `dice-baseball.club.v3.backup-schema3`。
- V2 不讀也不改 V1 的任何存檔。
- 所有寫入都在 ClubLock（Web Locks）內「讀最新存檔 → 計算 → 存檔」，並有 revision 檢查；不支援 Web Locks 的瀏覽器同一時間只允許一個分頁寫入。

## 指令

| 指令 | 用途 |
|---|---|
| `npm run test` | 全部測試（V1 + V2） |
| `npm run build` | 型別檢查並打包 |
| `npm run bench:v2` | 單場模擬效能 |
| `npm run bench:v2:idle` | 放置結算效能、存檔大小、滿員 30 人的升級與招募耗時 |
| `npm run balance:v2` | 養成、招募、經濟的平衡模擬（4 種玩家策略、14 天）；`SESSIONS=1 npm run balance:v2` 模擬一天上線 1 次 |

## 調整數值

- 比賽獎勵：`src/v2/domain/config.ts` 的 `REWARD_CONFIG`
- 升級成本、成長幅度、招募成本、人數上限：`src/v2/domain/progressionConfig.ts`

改完先跑 `npm run balance:v2` 看各策略的進度與勝率；改成長公式會影響之後所有比賽，但已經打完的比賽不會變。
